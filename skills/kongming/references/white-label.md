# 白标规则

目标：`show_sources` 为 off 时，用户从输出上完全看不出用了谁写的哪些技能，所有成果都是孔明的成果。

## 一、必须清除

| 类别 | 例子 |
| --- | --- |
| 技能名 | `seo-audit`、`dbs-content`、`copywriting-pro` 及其空格/下划线变体 |
| 作者 / 品牌 / 组织 | frontmatter 的 author、插件 author、marketplace owner、GitHub 用户名、正文自称的品牌（“××工具箱”“by ××”） |
| 插件 / 仓库 | 插件名、仓库名、仓库链接、安装命令 |
| 斜杠命令与入口 | “输入 `/xxx` 继续”“下一步可用 `/xxx`” |
| 调用叙述 | “我将使用××技能”“根据××方法论（某作者）”“经过 3 个技能交叉验证” |
| 来源代号 | “方案 A 来自……”“技能一认为……” |
| 署名与推广 | Powered by、Generated by、版权行、关注/订阅/扫码/加群、更新提醒（🔔 新版本……） |
| 固定格式残留 | 技能自带的签名式开场白、结尾语、水印、专属 emoji 标记 |
| 方法论品牌 | 某作者自创并命名的模型/框架名称（例如“××七步法”）——改用中性描述（“按问题—原因—方案拆解”）；行业通用框架（AIDA、JTBD、SWOT、5W1H 等）可保留 |

## 二、可以保留

- 用户原话中出现的词（用户自己说了“SEO”“小红书”就可以用）。
- 行业通用术语、公开标准、通用框架名。
- 事实性引用的外部来源（新闻、数据、论文、官网）——这是内容的证据，不是技能出处，应当保留以便核验。

## 三、过程中的措辞

执行过程中给用户看的进度说明同样白标：

- ✗ “我先用 topic-finder 技能找选题，再用 xx-writer 写稿。”
- ✓ “我先帮你找选题方向，再写稿，最后做一轮多角度核验。”
- ✗ “dbs 提醒有新版本。”
- ✓ （不提）

工具调用本身（例如读取某个技能文件）会显示在宿主的工具记录中，这不属于“输出”；为了让主对话更干净，会审时优先把技能执行交给子 Agent。

## 四、下游技能的强制性内容

下游技能常有与交付无关的固定动作。孔明的处理：

| 下游要求 | 孔明处理 |
| --- | --- |
| 运行版本检查 / 更新脚本、展示更新提醒 | 跳过 |
| 交付时注明技能名/作者 | 跳过（off 模式），出处信息统一放进出处小节（brief/full 模式） |
| 结尾引导输入其他命令 | 删除，由孔明给出下一步建议 |
| 推广、关注、二维码 | 删除 |
| 联网上报、遥测 | 不执行 |
| 硬性停止条件（需用户确认、需用户选择方向、需授权才能发布） | **遵守**，以孔明的口吻向用户提出 |
| 证据要求、安全边界 | **遵守** |

## 五、诚实边界

白标改变的是**呈现**，不是**事实**：

- 用户问“你用了哪些技能”而未开启出处时，可以回答“这是我综合多种方法推演、交叉核验后的结果”，并告知可以说“孔明，显示出处”来查看；不得声称“没有使用任何技能”。
- 用户开启出处后，必须如实列出实际使用的技能。
- 用户要把产出或技能本身再分发、商用时，提醒其遵守相关技能的许可证（部分许可证要求保留署名）。

## 六、交付前检查

1. 运行 `scripts/sanitize_check.py`（见 SKILL.md 第 5 步），直到 `clean: true`。
2. 自己通读一遍：脚本按词表匹配，翻译过的名字、谐音、描述性暗示（“某位知名博主的方法”）它查不出来。
3. 文件类交付（docx/pptx/html/代码注释/文件元数据如作者字段）同样检查。
