# 点将规则（动态路由）

用户的需求事先无法预知，所以不从固定模板里挑组合，而是每次从最终交付倒推。

## 一、读懂候选

`km.py scan` 给出每个候选的代号 `id`、脱敏后的 `description`、匹配分数 `score`、命中的跨语言概念 `concepts` 和画像状态 `profile`。判断时：

- **description 只用来初筛**。可能入选的，用 `km.py load <代号>` 读正文确认：它接收什么输入、交出什么、有哪些停止条件、需要什么工具或密钥。
- 名称关键词只能帮助发现，不能决定入选。
- 同名不同来源时，脚本已按“项目 > 用户 > 插件”保留一份；如正文显示它明显过时或残缺，换用其他候选。
- 需要外部工具/密钥/网络而当前环境不具备的，不入选，或只用它不依赖外部条件的部分。

把每个可能入选的候选在心里归纳成一行：**接手什么状态 → 交出什么东西；不交出什么**。

## 二、多语言匹配

需求和技能描述可能是不同语言（中文需求 + 英文技能、日文需求 + 中文技能……）。`km.py scan` 用三层信号排序：

1. **字面**：Unicode 归一（全半角、大小写、去重音），英文轻量词干化，中日韩文字切二元组；技能名权重 ×3。
2. **概念**：`scripts/lexicon.json` 把同一概念的多语言说法（中、英、日、韩、西、法、德）映射到同一概念 ID，例如「选题 / topic ideas / ネタ / 주제 선정」→ `topic_ideation`。需求与技能命中同一概念即加分。用户可在 `~/.kongming/lexicon.json` 追加自己的说法。
3. **画像**：模型为每个技能写下的多语言关键词与双语摘要（`~/.kongming/profiles.json`），弥补技能描述只用一种语言、措辞偏门的问题。技能内容一变（哈希不同），画像自动标为 stale，下次补写。

再加上 `--keywords`：每次检索时由你把需求翻译成多语言关键词一起传入。三层信号用 BM25 合并排序，**最后由你对前 20 名做语义判断**——分数只决定看谁，不决定用谁。

## 三、倒推拆解

1. 写出最终交付；找出“交出”能直接满足它的候选。
2. 看它要“接手”的状态当前是否已具备。不具备时，找能交出该状态的候选，依此向前推，直到接上用户当前状态。
3. 用户已经具备的状态（例如已经定好选题、已经有初稿），对应步骤跳过。
4. 交付需要的东西写在某候选的“不交出”里时，不让它承担这一步。
5. 只能由用户产出的状态（提供材料、做出选择），写成用户回应点，放在需要它的步骤之前。

拆解结果是一串步骤，随每步实际产出更新，不是一次定死的长链。

## 四、每一步选几个人

对每一步，把候选分成三档：

| 档位 | 含义 |
| --- | --- |
| 对口 | 方法明确针对这一步的交付，正文流程完整 |
| 相邻 | 能做，但只覆盖一部分，或针对相近但不同的问题 |
| 无关 | 只是关键词撞上 |

然后：

- 只有一个对口 → **单将**；任务质量要求高时，加模型本家做会审（若 `native_voice` 为 true）。
- 两个及以上对口 → **会审**，取最互补的 `max_skills` 个（方法论差异越大，交叉验证价值越高；几乎同质的只留一个）。
- 只有相邻 → 用相邻技能负责其覆盖部分，其余由模型本家补齐；必要时会审。
- 没有对口也没有相邻 → **独断**，由模型本家完成。不要把不对口的方法硬套上去。

## 五、常见任务的拆法示例

这些只是思路示例，实际以本机已安装的技能为准：

| 需求 | 典型拆法 |
| --- | --- |
| “帮我写一篇能上搜索首页的文章” | 关键词/选题研究 → 大纲 → 写作（会审）→ SEO 优化与校对 |
| “下周发什么内容” | 账号/受众诊断（如有材料）→ 选题生成（会审）→ 选题评估排序 |
| “分析一下这个产品” | 用户需求/场景分析 ∥ 竞品与市场分析 ∥ 商业模式分析（并行，合成一份）→ 结论与建议 |
| “把这段文案改好” | 诊断问题 → 改写（会审）→ 校对 |
| “这个方案行不行” | 先设闸门：关键前提是否成立 → 成立再做细化评估，不成立直接给出改道建议 |

## 六、结构与合并

| 结构 | 适用 | 注意 |
| --- | --- | --- |
| 单项 | 一个方法就能完成 | 默认 |
| 串行（连环） | 后一步要用前一步的交出 | 用交接包传递 |
| 并行 | 同一对象上多个互不依赖的分析 | 最终成品只由一人执笔 |
| 会审 | 多个成员交出同一种东西 | 按 council.md 交叉验证 |
| 闸门 | 某一步回答“该不该继续” | 放在会白做的工作之前 |

合并方式：直接传递（串行）、合成一份（并行各看一面）、交叉验证后定稿（会审）、交给用户挑（取决于用户偏好）、分别交付（几个独立问题）。

## 七、交接包

串行交接时，下一个成员收到：

- 原始材料与约束（原样保留）
- 已确认事实
- 上一步交出
- 待验证假设
- 这一步要交出什么
- 怎样算合格

## 八、何时重新点将

- 关键前提被新事实推翻，或上一步交出改变了后续步骤的必要性；
- 用户指出结果偏离目标，或提出新约束；
- 所用方法走不通，且能指出具体缺口。

用户只是补充材料或说“继续”，不等于需要换人；先定位缺口。
